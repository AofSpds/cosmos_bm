# 1. One-page executive view

## 1.1 Roadmap thesis

Cosmos Hub does not become a 6G network, a telecom operator, or a proprietary AI router. The roadmap selectively applies autonomous-network management prior art to the existing four-BM strategy.

```text
Current Interchain stack
IBC / Eureka / DEX / Bridge / Relayer / Skip Go / Wallet / Mintscan
        ↓
Evidence foundation
normalized route, leg, finality, failure, recovery and revenue evidence
        ↓
Service assurance
metric → SLO → signed SLA → exception → recovery → bounded compensation
        ↓
Bounded intelligence
AI prediction → deterministic optimization → hard policy → explicit authorization
        ↓
Provider competition
signed capabilities, quotes, histories, concentration controls and switching
        ↓
Enterprise abstraction
structured intent, service class, policy adapter, institutional receipt and reconciliation
```

## 1.2 Selected concept portfolio

| Class | Concepts | Primary BM |
|---|---|---|
| **SELECT** | Observability/Evidence; Interchain SLO/SLA; Structured Intent/Capability Exposure | BM2, BM3, BM4 |
| **SELECT-LIMITED** | Bounded AI Control; Predictive Assurance; Sequential Failover; Conflict Arbitration; draft-only Natural-language Intent Assistant | BM2, BM3, BM4 |
| **EXISTING/ASSESS** | Candidate Route Diversity; Smart-Swap Split Routing | BM2 baseline |
| **WATCH** | Replay/Simulation; Agentic/Multi-agent Orchestration; Redundant/Hedged Execution | Independent research only |
| **REJECT** | Zero-touch live asset actuation; literal slicing; RAN/PHY transfer; Hub-owned proprietary AI router | None |

## 1.3 BM connection

| BM | Roadmap role |
|---|---|
| **BM1 — Interchain Asset Distribution Market** | Starts without AI dependency. Uses observability for campaign attribution, anti-gaming, revenue proof and retention measurement. |
| **BM2 — Assured Interchain Delivery SLA** | Main technical integration point: evidence, SLO/SLA, bounded prediction, deterministic scoring, provider quote/bond/receipt and limited failover. |
| **BM3 — Enterprise One-Connection Gateway** | Main abstraction point: structured intent, capability catalog, policy adapter, service tiers, institution authorization, receipt and reconciliation. |
| **BM4 — Asset & Service Registry** | Factual asset/provider/capability/history records, evidence freshness, bond reference and incident history. No “Hub Approved/Safe/Compliant” labels. |

# 2. Hard locks and non-goals

## 2.1 Preserved locks

- Four BMs and their order remain unchanged.
- Base IBC stays open and untolled by default.
- Hub remains non-custodial, non-exclusive and non-competing with application providers.
- ATOM is not a mandatory payment asset.
- KYC source material and PII are not stored on-chain.
- Commercial revenue must be externally paid, separately accounted and transparently linked to the Revenue Vault.
- Contracts/data and small CosmWasm MVPs precede native modules.
- AI cannot hold keys, authorize transactions, mutate hard policy, weaken finality/minimum receive, exceed exposure caps or decide compensation alone.
- No global atomic revert, principal guarantee, insurance or regulatory-compliance implication.

## 2.2 Explicit non-goals

```text
NOT a new bridge
NOT a Hub DEX or stablecoin
NOT a fifth BM
NOT a telecom network implementation
NOT a network-slicing product
NOT a 6G conformity programme
NOT an autonomous treasury or trading agent
NOT a single mandatory router
NOT production architecture approval
```

# M1 — Observability & SLO Foundation

```text
START CONDITION = M0 selected portfolio approved
DEPENDENCY = accessible events/APIs, provider cooperation for non-public fields
PRIMARY DELIVERABLES = telemetry schema, time model, failure/recovery taxonomy, deterministic baseline suite, SLO dictionary
PRIMARY ACTORS = indexer/data engineers, router/relayer providers, SLA/product design, independent auditor
ON-CHAIN = optional schema hashes/references only; no customer data
OFF-CHAIN = telemetry, features, analytics, dashboards and code
```

### Minimum evidence schema

| Domain | Mandatory fields |
|---|---|
| Request/quote | request ID, asset, amount, route, provider, fee, minimum output, expiry, SLO/SLA template and signature |
| Source chain | tx hash, inclusion time, finality criterion/time, result |
| Route leg | protocol, source/destination chain, asset representation, start/end event, status, fee/gas, evidence source |
| Destination | tx/state evidence, inclusion/finality, realized amount |
| Recovery | last-known asset location, recovery address, action, owner, result and duration |
| Classification | provider-controlled, user-caused, external chain/protocol event, exempt, unresolved |
| Provenance | data source, version, timestamp, signature/hash, freshness and confidence |
| Model readiness | feature time, label time, missingness, leakage flag and reproducibility reference |

### Deterministic baseline suite

```text
current Skip Go/default route
shortest path
lowest quoted cost
maximum quoted output
minimum hop
rule-based weighted score
```

Where a comparator is unsupported for a route, the absence is recorded; it is not silently approximated.

### Candidate M1 guardrails to freeze before data collection

- 100% of pilot-scope transactions carry a unique execution/request ID.
- 100% of required source/destination evidence fields are either present or explicitly marked missing with reason.
- Last-known asset location is reconstructable in every simulated failure case before a live M3 route is authorized.
- Provider self-report is not the sole evidence for commercial completion or breach.
- Timestamp source and finality criterion are explicit for every supported chain/protocol.

### Exit

| PASS | HOLD | KILL |
|---|---|---|
| G2 data coverage and provenance are sufficient; G3 baselines reproducible | failure/recovery labels too sparse, time semantics inconsistent, or independent source unavailable | selected pilot scope cannot reconstruct completion/recovery or violates privacy boundary |

**Claim ceiling:** C1–C2.  
**No live AI or commercial SLA is authorized at M1.**

# M2 — Shadow Intelligence

```text
START CONDITION = M1 data and baseline gates passed for a bounded route universe
DEPENDENCY = frozen dataset, feature/label definitions and evaluation protocol
PRIMARY DELIVERABLES = shadow models, calibration/drift report, baseline comparison, abstention/fallback specification
PRIMARY ACTORS = independent model providers/researchers, data engineering, validator/auditor
ON-CHAIN = none; optional model/version reference only after evaluation
OFF-CHAIN = all training, inference and evaluation
```

### Models allowed

- completion-time distribution;
- realized output/slippage;
- failure probability;
- recovery probability and expected recovery duration;
- provider health/anomaly;
- risk-adjusted candidate score.

### Evaluation protocol

1. Pre-register dataset split, route universe, metrics and decision thresholds.
2. Prevent future information leakage: features must exist at quote/decision time.
3. Compare against every applicable deterministic baseline.
4. Evaluate calibration, not only ranking accuracy.
5. Test stale/missing data, provider outage, chain halt, price movement and model drift.
6. Require abstention and deterministic fallback below confidence threshold.
7. Report added compute/API latency and operating cost.

### Measurements

| Area | Candidate metric | Intuitive meaning |
|---|---|---|
| Output | realized-output error; regret versus best feasible route | how much value the prediction misses |
| Latency | MAE/quantile loss and p95 error | whether the model estimates normal and tail completion time |
| Failure | Brier score, precision/recall at action threshold | whether predicted probabilities match actual failures |
| Calibration | expected calibration error/reliability curve | whether “10% risk” really fails about 10% of the time |
| Drift | feature/output drift and performance decay | whether the world changed after training |
| Safety | abstention and fallback success | whether uncertainty returns control to the safe baseline |
| Economics | incremental route value minus compute/API/ops cost | whether intelligence pays for itself |

Thresholds are frozen in the evaluation plan before model comparison; they are not tuned after seeing results.

### Exit

| PASS | HOLD | KILL |
|---|---|---|
| reproducible out-of-sample improvement, acceptable calibration, safe abstention and positive net value | data remains sparse or gain unstable across route segments | no material gain over deterministic baseline, unsafe calibration, unbounded drift or excessive cost |

**Claim ceiling:** C2.  
**Live actuation:** prohibited.

### Ordered evaluation

1. Candidate route diversity — existing baseline.
2. Pre-execution provider/client/channel health check.
3. Sequential route replacement before authorization.
4. Bounded post-authorization retry only where idempotency is proven.
5. Split routing evaluation with per-leg receipts.
6. Redundant/hedged execution remains a separate optional track and default-off.

### Mandatory multi-leg invariants

```text

route-plan hash
per-leg amount and exposure cap
leg start/complete/fail state
aggregate completion rule
last-known asset location
duplicate suppression
recovery owner and deadline

```

### Net route value

```text
incremental success/output/tail-latency benefit
- extra provider fee
- extra gas
- liquidity/price impact
- recovery and support cost
- locked-capital cost
- compliance/accounting overhead
= net route value
```

### Neutrality controls

- open capability and quote schema;
- provider switching;
- deterministic eligibility separate from model rank;
- confidence intervals and data-quality disclosure;
- concentration KPI and alert threshold;

| PASS | HOLD | KILL |

# M6 — Adaptive Closed-loop Scale

```text
START CONDITION = operating evidence across M3–M5; stable data/model, safety, neutrality, legal and economic results
```

### Allowed adaptation

- update advisory provider/route weights within a frozen policy envelope;
- change model version through governed release/rollback;
- abstain and fall back when confidence or data quality falls;
- trigger alerts, manual review, pause or route removal under deterministic rules;
- use verified outcomes to improve future prediction.

### Still prohibited

- autonomous key control;
- unapproved transaction;
- model-driven exposure-cap increase;
- automatic addition of an unregistered bridge/provider;
- silent finality or recovery-policy weakening;
- autonomous compensation adjudication;
- “full zero-touch” claim that erases human/institution authority.

### Exit

| PASS | HOLD | KILL/PIVOT |
|---|---|---|
| stable calibration, bounded adaptation, positive economics, no concentration breach, manageable incidents and repeated external revenue | benefits are narrow, governance latency high or operating cost marginal | dynamic loop is less safe/economic than static deterministic control; revert permanently to bounded static service |

# 7. Gate system G0–G8

| Gate | PASS evidence | HOLD trigger | FAIL/KILL trigger | Principal stage |
|---|---|---|---|---|
| **G0 Evidence** | first-party source, exact status/version/date and citation | source not archived or status uncertain | marketing article only | M0 |
| **G1 Transferability** | actual Cosmos object, state and actor mapping | mapping is mostly analogy | radio/RAN property is essential | M0 |
| **G2 Data** | features/labels/provenance/freshness measurable | rare failure labels or independent source missing | objective state cannot be reconstructed | M1 |
| **G3 Baseline** | current and deterministic comparators reproducible | comparator unsupported for part of universe | improvement cannot be measured or replicated | M1–M2 |
| **G4 Safety** | hard constraints, authorization, fallback, pause, audit and recovery | idempotency/asset location uncertain | AI controls keys/assets/policy or duplicate execution possible | M3–M4 |
| **G5 Neutrality** | multiple providers, open spec, switching and concentration KPI | thin market or dominant provider | exclusive operator/Hub competition | M3–M6 |
| **G6 Economic** | positive measured net value, WTP and bounded operating cost/exposure | narrow benefit or unresolved reserve | operating/compensation cost exceeds revenue | M3–M6 |
| **G7 Claim** | wording matches source and measured maturity | outcome not yet published/verified | standard/compliance/guarantee overclaim | all stages |
| **G8 Integration** | strengthens one of four BMs without core-thesis change | unclear BM owner/value | fifth BM or architecture expansion | M0 and revision scope |

### 7.1 Gate binding

- Every PASS is bound to exact source/version, schema, code, dataset, model or contract scope.
- A later material change reopens only the affected gate, not a global validation loop.
- A failed optional track does not invalidate unrelated tracks.
- No gate can be passed solely by self-reported provider evidence when financial rights or breach are affected.

## 9.2 Answers to timing questions

### Must AI routing precede BM1?

**No.** BM1 starts from contract, attribution, anti-gaming and revenue evidence. AI routing is not a dependency. BM1 can become the earliest source of higher-quality route and usage telemetry.

### Can telemetry accumulate before BM2?

**Yes, partially.** BM1, current Skip Go tracking, chain events and indexers can populate successful-route and timing records. Failure, recovery, provider-control and commercial-breach labels still require deliberate M1 design and provider cooperation.

### Can existing Skip Go data support early model research?

**Potentially, but not assumed.** Public status and route APIs establish current features and state categories. Historical depth, feature timestamps, failed-route sampling, label licensing and provider-level availability must pass G2 before model claims.

### Can service abstraction be tested before BM3?

**Yes, as UX only.** A wallet or sandbox can test structured-intent creation, validation and disclosure. It must not become a direct natural-language transaction path or imply enterprise SLA readiness.

### Should multi-path precede paid SLA demand?

**No.** Route diversity already exists. More complex failover/split/hedged mechanisms add cost and recovery surface, so they follow evidence of paid assurance demand and a measurable net-route-value case.
